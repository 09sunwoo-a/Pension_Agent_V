# 09. 보안 / Secret 취급

> 근거: `sources/KB_GenAI_ProAgent_SourceOfTruth_v2.md` §22, §39
> 이 문서의 규칙에는 **예외가 없다.**

---

## 1. Secret으로 취급하는 값

```text
LLM API Key                       (kb-key / LLM_API_KEY_TRNN / LLM_API_KEY_SERV)
Fabrix OpenAPI Token              (x-openapi-token)
Fabrix Generative AI Client       (x-generative-ai-client)
기타 Client ID / Client Secret
```

`x-generative-ai-client` 값은 JWT 형태이고 **payload에 `clientSecret` 이 들어 있다.**
"헤더 식별자"처럼 보이지만 **자격증명이다.**

---

## 2. 금지 사항

```text
❌ 소스 코드에 하드코딩
❌ 저장소에 커밋 (.env 포함)
❌ 로그 / print / console.log 출력
❌ 문서 · 이슈 · PR · 채팅에 붙여넣기
❌ 정적 JS 파일에 포함해서 배포
```

코딩 에이전트에게도 동일하게 적용된다.
**실제 Secret 값을 받지 않는다. 필요한 것은 변수 "이름"과 stage 분기 구조뿐이다.**

---

## 3. 환경변수 이름 (값 아님)

`agent/.env.example` 에 이름만 유지한다. 실제 `.env` 는 커밋하지 않는다.

```text
ENV_PATH                  ← Jenkins가 --build-arg ENV_FILE_PATH 로 주입 (training / serving)

LLM_BASE_URL_TRNN
LLM_BASE_URL_SERV
LLM_API_KEY_TRNN
LLM_API_KEY_SERV
LLM_MODEL
LLM_API_VERSION
LLM_DEPLOYMENT_NAME       (선택 — 미설정 시 코드 기본값)
LLM_CLIENT_USER_SPREAD
LLM_MAX_RETRIES
LLM_TIMEOUT
```

프론트/Fabrix 쪽(브라우저에서 필요한 값):

```text
FABRIX_ENDPOINT_URL
FABRIX_AGENT_ID
FABRIX_OPENAPI_TOKEN            ← Secret
FABRIX_GENERATIVE_AI_CLIENT     ← Secret
```

## 4. ⚠️ 브라우저 direct call의 토큰 노출 문제

이 프로젝트에서 **가장 중요한 미해결 보안 과제**다.

```text
기술적으로 Browser direct call 성공     ← 검증됨
                  ≠
운영 보안상 token 노출 허용              ← 별개 문제
```

정적 JS에 토큰을 하드코딩하면:

```text
누구나 DevTools → Sources 에서 읽을 수 있다
Network 탭 요청 헤더에도 그대로 보인다
브라우저/프록시 캐시에 남는다
```

`zmnbank.kbstar.com` 이 사내망이라 해도, **화면에 접근 가능한 모든 사용자에게
Fabrix 호출 권한이 그대로 노출**된다는 뜻이다.

### 검토해야 할 대안

```text
A. 사내 WAS에 얇은 proxy endpoint 를 두고 토큰은 서버에만 보관
   브라우저 → 사내 WAS(세션 인증) → Fabrix
   → 토큰이 브라우저에 내려가지 않는다. 가장 안전.

B. 짧은 수명의 토큰을 서버에서 발급받아 사용

C. 정적 JS에 장기 토큰 하드코딩
   → 진단/PoC 한정. 운영 반입 전 제거 필수.
```

**운영 설계 전에 반드시 사내 보안정책을 확인하라.**
이 저장소는 A안을 권장하지만, 최종 결정은 보안 검토 사항이다.

## 5. 진단용 토큰을 쓸 때

Fabrix 연결 진단 코드는 토큰 없이 돌지 않는다. 그럴 때의 규칙:

```text
[ ] 진단 코드는 별도 파일/별도 브랜치로 분리한다
[ ] 저장소에 커밋하지 않는다
[ ] 테스트가 끝나면 즉시 제거한다
[ ] 노출된 적이 있는 토큰은 폐기(rotate)한다
[ ] "테스트용"이라는 이유로 운영 배포에 남기지 않는다
```

> 📌 **기록:** `pension_fabrix_was_test_windows_1.zip` 로 전달된 WAS 진단본
> (`pensionAgentDemo.js` 에 `FABRIX_TEST_CONFIG` 추가)에는 실제
> `openapiToken` / `generativeAiClient` / `agentId` / 직원 ID가 **평문으로** 들어 있었다.
> 그래서 **이 저장소에는 반입하지 않았다.**
> 해당 토큰들은 이미 파일로 유통됐으므로 **폐기·재발급 대상으로 보는 것이 안전하다.**
> 동일한 진단이 다시 필요하면 토큰을 소스 밖(입력/설정)에서 주입하는 형태로 다시 작성하라.

## 6. 로그

```python
# ❌
print("headers:", headers)          # kb-key 노출
print("[ERROR]", traceback.format_exc())   # 키가 섞여 나올 수 있음

# ✅
print("[ERROR]", repr(e))
print("llm status:", {"stage": ..., "api_key_set": True})   # 값이 아니라 여부만
```

`llm_client.status()` 가 `api_key_set: bool` 만 반환하는 것도 같은 이유다.
**이 패턴을 깨지 마라.**

## 7. 커밋 전 체크리스트

```text
[ ] .env 가 스테이징에 없는가          (git status / .gitignore)
[ ] 토큰·키 문자열이 diff에 없는가
[ ] JWT 형태 문자열(eyJ...)이 없는가
[ ] 직원 ID 등 개인식별정보가 없는가
[ ] 로그 출력에 Secret이 섞이지 않는가
```

빠른 확인:

```bash
git diff --cached | grep -nE 'eyJ[A-Za-z0-9_-]{10,}|kb-key|api[_-]?key|token|secret' -i
```

> 저장소의 고객 데이터는 전부 **더미 데이터**다. 실제 고객 정보를 넣지 마라.
