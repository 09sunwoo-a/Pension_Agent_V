## 1. 코드 구조 — 평면(flat) 구조다

배포 컨테이너의 실제 모습:

```text
/custom/
├─ .env
├─ main.py
├─ llm_client.py
└─ requirements.txt
```

```text
✅ main.py 는 repository root 에 있다
✅ llm_client.py 도 repository root 에 있다
✅ uvicorn 은 main:app 으로 실행한다

❌ app/main.py 구조가 아니다
❌ from app.output_schema import ... 같은 package import 금지
```

> **이 저장소에서는 `agent/` 아래에 두지만, 사내 GitLab 배포 repo에서는 root 평면 구조다.**
> 디렉터리 매핑은 [03-배포-파이프라인.md](03-배포-파이프라인.md) 참고.

### 새 Python 파일을 추가할 때

Git에 파일을 추가하는 것만으로는 **컨테이너에 들어가지 않는다.**
현재 Dockerfile은 와일드카드가 아니라 파일 단위 `COPY` 다.

```dockerfile
COPY ./.env /custom/.env
COPY ./main.py /custom/main.py
COPY ./llm_client.py /custom/llm_client.py
```

`output_schema.py` 를 추가했다면 반드시:

```dockerfile
COPY ./output_schema.py /custom/output_schema.py
```

를 같이 추가한다.

> 실제 사고: `from app.output_schema import ...` + `COPY` 누락
> → `ModuleNotFoundError: No module named 'app'`
> → Pod 기동 실패 → `Progressing` → `Degraded` → Health Check Timeout → rollback
> 자세한 내용은 [08-트러블슈팅.md](08-트러블슈팅.md).

## 3. Gemma4 호출 규격 (검증된 조합)

STG TRNN에서 실제 성공한 조합이다. **추측으로 바꾸지 마라.**

| 항목 | 값 |
|---|---|
| Client | `langchain_openai.AzureChatOpenAI` |
| Endpoint (TRNN) | `https://cm-hea-genai-stg-apim.azure-api.net/trnn/gemma-4` |
| Endpoint (SERV) | `https://cm-hea-genai-stg-apim.azure-api.net/serv/gemma-4` |
| Deployment Name | `gemma-4-31b-nvidia-fp4-h100` |
| OpenAI API Version | `"1"` (문자열) |
| Custom headers | `kb-key`, `x-client-user` |

```python
headers = {
    "kb-key": api_key,
    "x-client-user": f"{user_id}-{random_suffix}",
}

llm = AzureChatOpenAI(
    openai_api_version="1",
    deployment_name="gemma-4-31b-nvidia-fp4-h100",
    streaming=False,
    stream_usage=True,
    default_headers=headers,
    api_key=api_key,
    azure_endpoint="https://cm-hea-genai-stg-apim.azure-api.net/trnn/gemma-4",
    model_kwargs={"extra_headers": headers},
    max_tokens=max_tokens,
)
```

### ⚠️ 가장 중요한 함정

```text
Endpoint 마지막 path : gemma-4
Deployment name      : gemma-4-31b-nvidia-fp4-h100
```

**둘은 다르다.** endpoint path를 보고 `deployment_name = "gemma-4"` 로 추측하면 실패한다.

### 스테이지 분기

`llm_client.py` 는 `ENV_PATH` 환경변수로 TRNN/SERV를 가른다.
`ENV_PATH` 는 Jenkins가 `--build-arg ENV_FILE_PATH=training` 으로 주입한다.

```text
ENV_PATH in {"serving", "serv"}  → SERV
그 외 (기본)                      → TRNN
```

## 4. `llm_client.call()` 인터페이스

**이 시그니처를 유지하라.** 바꾸기 전에 반드시 현재 파일을 먼저 읽는다.

```python
call(
    messages: list[dict[str, str]],
    *,
    system: str = "",
    model: str = "",          # deployment_name override
    max_tokens: int = 1024,
    x_client_user: str = "",
) -> str
```

부가 함수:

- `status() -> dict` — stage / endpoint / deployment / api_key_set 진단용.
  **API key 값 자체는 반환하지 않고 `api_key_set: bool` 만 반환한다.** 이 원칙을 깨지 마라.
- `python llm_client.py` 로 직접 실행하면 연결 테스트가 돈다.

## 6. `input_value` 는 **문자열**이다

Fabrix → Agent 구간에서 `input_value` 는 문자열이다.
이 프로젝트는 그 문자열 안에 다시 JSON을 넣는 방식을 쓴다.

```json
{
  "message": "IRP 세액공제 한도가 얼마야?",
  "x_client_user": "<직원ID>"
}
```

이 객체를 **직렬화한 문자열**로 전달한다.

Agent 쪽은 방어적으로 처리한다 — JSON이 아닐 수도 있다고 가정한다.

```python
def parse_input_value(raw: str) -> dict[str, Any]:
    try:
        parsed = json.loads(raw)
        if isinstance(parsed, dict):
            return parsed
    except Exception:
        pass
    return {"message": raw}
```

그 뒤 필드를 여러 후보에서 꺼낸다 (`main.py` 현재 구현):

```python
user_question = str(
    parsed.get("message") or parsed.get("input_value") or req.input_value
).strip()

x_client_user = str(
    parsed.get("x_client_user") or parsed.get("user_id") or "test-user"
)
```

## 7. LLM 프롬프트 규칙

LLM은 **slot 하나당 문장 하나**를 만든다. JSON/Markdown/라벨/불릿을 만들지 않는다.

현재 `generate_text_slot()` 의 시스템 프롬프트가 강제하는 것:

```text
- JSON을 출력하지 않는다.
- Markdown을 출력하지 않는다.
- 제목이나 라벨을 붙이지 않는다.
- bullet 기호를 사용하지 않는다.
- 코드블록을 사용하지 않는다.
- 요청한 문장 자체만 출력한다.
- 모르는 사실을 임의로 만들지 않는다.
```

### ⚠ 알려진 품질 이슈 (구조 문제 아님)

Gemma가 아래 같은 **메타 발화**를 생성한 사례가 있다.

```text
"작성해 드립니다."
"저는 ... 도와드립니다."
```

프롬프트에 다음을 명시해서 억제한다.

```text
사용자 질문에 직접 답한다.
자신의 역할이나 작성 행위를 설명하지 않는다.
"작성하겠습니다", "도와드립니다" 같은 메타 표현을 쓰지 않는다.
```

> 이건 **Prompt 품질 문제**이지 구조 문제가 아니다.
> 이 증상을 보고 출력 계약이나 파이프라인을 뜯어고치지 마라.

## 8. 현재 `main.py` 흐름

```text
POST /chat
  ↓ parse_input_value(req.input_value)
  ↓ user_question / x_client_user 추출
  ↓
  ├─ generate_text_slot(lead,    max_tokens=180)   # 핵심 결론 1문장
  ├─ generate_text_slot(detail,  max_tokens=350)   # 상세 2~3문장
  └─ generate_text_slot(caution, max_tokens=180)   # 주의사항 1문장
  ↓
build_fact_answer(lead, detail, caution)   ← Python이 100% 구조 고정
  ↓
AnswerEvent(data=answer)
  ↓ 예외 시 ErrorEvent(message=...)  ← 오류 구조도 Python이 고정
  ↓
build_streaming_response()  →  SSE `data: {JSON}\n\n`
```

### 개선 여지 (작업 시 참고)

현재 구현은 **slot마다 LLM을 1회씩, 총 3회 순차 호출**한다.
지연이 문제가 되면 아래를 검토하라. 단, 어느 쪽도 "LLM이 구조를 만든다"로 가면 안 된다.

- 3개 slot을 한 번의 호출로 받되 **구분자 기반**으로 분리 (JSON 금지)
- `asyncio` 병렬화 (단, `call()` 은 현재 동기 함수다)

## 9. 오류 처리 원칙

예외가 나도 **프론트가 파싱 가능한 구조**를 돌려준다.

```python
except Exception as e:
    print("[ERROR]", repr(e))          # 로그에 Secret이 섞이지 않게 주의
    logical_event = ErrorEvent(message="답변 생성 중 오류가 발생했습니다.")
```

```text
✅ 사용자에게는 일반화된 메시지
✅ 상세 원인은 컨테이너 로그로
❌ 예외 원문/스택/키를 그대로 content에 담지 않는다
```
