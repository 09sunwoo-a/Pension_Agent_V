# 1. 문서 목적

본 문서는 개인형 IRP 사후관리 Agent의 Golden Case를 제작할 때 사용할 **고객 DATA의 기본 구조와 작성 원칙**을 정의한다.

이 구조의 목적은 실제 운영계 DB Schema를 확정하는 것이 아니다.

이미 설계된 고객별 BRIEF를 바탕으로,

- 실제 고객처럼 자연스러운 고객정보
- 계좌 및 보유상품 현황
- 최근 고객에게 발생한 이벤트
- 외부 금융정보
- 비대면 행동
- 과거 상담이력
- Badge

를 일관된 형태로 구성하기 위한 **Golden Case 제작용 Data Model**이다.

따라서 모든 고객이 모든 필드를 가져야 하는 것은 아니다.

Case 판단에 필요한 데이터를 중심으로 구성하며, 새로운 Case에서 필요한 정보가 발견되면 필드를 추가할 수 있다.

# 2. 전체 구조

고객 데이터는 크게 세 영역으로 구분한다.

```text
고객 DATA
│
├─ ① 화면직접표시데이터
│    실제 화면에 그대로 표시되는 고객·계좌·상품정보
│
├─ ② 에이전트판단용데이터
│    Agent가 고객상황을 해석할 때 활용하는 Timeline / 외부정보 / 행동 / CRM
│
└─ ③ 파생데이터
     RAW DATA에서 계산하거나 Rule로 생성한 값과 Badge
```

핵심 원칙은 다음과 같다.

**화면직접표시데이터**
→ 화면에서 그대로 사용되는 사실값

**에이전트판단용데이터**
→ Agent가 고객의 상황과 맥락을 해석하기 위한 Evidence

**파생데이터**
→ 날짜 차이, 비중, 대기기간, Badge 등 원천값에서 계산 가능한 정보

# 4. 메타정보

고객 DATA 자체의 기준을 관리한다.

| 필드 | 설명 | 예시 |
|---|---|---|
| `케이스ID` | Golden Case 관리용 ID | `B01-03` |
| `데이터구분` | 실제 / 테스트 / 시연 구분 | `시연용가상고객` |
| `기준일` | 모든 D-day 및 계좌 상태의 기준일 | `2026-09-11` |

예시:

```json
{
  "메타정보": {
    "케이스ID": "B01-03",
    "데이터구분": "시연용가상고객",
    "기준일": "2026-09-11"
  }
}
```

# 5. 화면직접표시데이터

화면에서 별도의 LLM 생성 없이 그대로 표시할 수 있는 데이터다.

가능하면 이 영역의 값은 Agent가 다시 생성하지 않는다.

---

## 5.1 고객정보

현재 상세화면에서 기본적으로 보여주는 고객 정보.

| 필드 | 설명 | 예시 |
|---|---|---|
| `고객식별자` | 10자리 고객 식별번호 | `12345-67890` |
| `고객명` | 시연용 가상 고객명 | `김서연` |
| `나이` | 만 나이 | `44` |
| `성별` | 남 / 여 | `여` |
| `스타클럽등급` | 고객 스타클럽 등급 | `VIP` |
| `투자성향` | 현재 유효한 투자성향 | `위험중립형` |
| `IRP계좌신규일` | 개인형IRP 신규일 | `2019-03-15` |
| `디폴트옵션` | 등록 상태 및 상품 | 아래 구조 참고 |

### 스타클럽등급

다음 네 값만 사용한다.

```text
VVIP
VIP
그랜드
베스트
```

### 디폴트옵션

```json
{
  "등록여부": true,
  "상품명": "뿔려드림 2호",
  "화면표시": "등록 · 뿔려드림 2호"
}
```

미등록 고객:

```json
{
  "등록여부": false,
  "상품명": null,
  "화면표시": "미등록"
}
```

## 5.2 IRP계좌현황

고객 상세화면의 IRP 계좌 요약영역.

| 필드 | 설명 |
|---|---|
| `평가금액` | IRP 전체 평가금액 |
| `원리금보장형금액` | 원리금보장형 자산 합계 |
| `원리금보장형비중` | 전체 대비 비중 |
| `실적배당형금액` | 실적배당형 자산 합계 |
| `실적배당형비중` | 전체 대비 비중 |
| `고유계정대금액` | 현금성 / 고유계정대 금액 |
| `고유계정대비중` | 전체 대비 비중 |
| `계좌수익률` | 화면에 표시되는 IRP 계좌 수익률 |
| `세액공제잔여한도` | 확인 가능한 잔여 공제한도 |
| `최근상품신규일` | 가장 최근 신규 상품 가입일 |
| `최근신규상품명` | 해당 상품명 |

예시:

```json
{
  "IRP계좌현황": {
    "평가금액": 45000000,

    "원리금보장형금액": 28000000,
    "원리금보장형비중": 62,

    "실적배당형금액": 15000000,
    "실적배당형비중": 33,

    "고유계정대금액": 2000000,
    "고유계정대비중": 5,

    "계좌수익률": 3.1,

    "세액공제잔여한도": 5000000,

    "최근상품신규일": "2026-06-12",
    "최근신규상품명": "키움 더드림 단기채"
  }
}
```

금액은 화면 표시문구가 아닌 **원 단위 숫자**로 저장한다.

```text
45000000 → 화면에서 4,500만원으로 표시
```

비중 역시 가능한 경우 평가금액을 기준으로 계산하여 사용한다.

# 6. 보유상품현황

IRP 상세화면의 `운용 현황 자세히` 영역에 표시되는 데이터다.

```json
{
  "보유상품건수": 3,

  "보유상품": [
    {
      "상품ID": "H001",
      "상품명": "KB저축은행 정기예금 1년",
      "유형": "원리금보장",
      "평가금액": 28000000,
      "비중": 62,
      "1년수익률": 4.3
    },

    {
      "상품ID": "H002",
      "상품명": "키움 더드림 단기채",
      "유형": "실적배당",
      "평가금액": 15000000,
      "비중": 33,
      "1년수익률": 2.3
    },

    {
      "상품ID": "H003",
      "상품명": "현금성자산",
      "유형": "대기",
      "평가금액": 2000000,
      "비중": 5,
      "1년수익률": 0.2
    }
  ]
}
```

Golden Case에 필요하면 다음 정보를 추가할 수 있다.

- 가입일
- 만기일
- 약정금리
- 위험등급
- 상품판매상태
- 상품분류
- 평가손익

단, 화면에서 사용하지 않거나 Case 판단에도 필요하지 않은 필드는 억지로 생성하지 않는다.

# 7. 에이전트판단용데이터

이 영역은 고정된 원장 Schema라기보다 **Agent가 고객상황을 판단하는 Evidence Pool**이다.

Case에 따라 필요한 데이터만 구성할 수 있다.

## 7.1 최근거래및변화

고객에게 최근 발생한 주요 이벤트를 시간순으로 기록한다.

예:

```json
{
  "최근거래및변화": [
    {
      "이벤트ID": "T001",
      "발생일": "2026-05-15",
      "이벤트유형": "정기예금만기",
      "관련상품ID": "H001",
      "금액": 12000000,
      "처리결과": "현금성자산 전환"
    },

    {
      "이벤트ID": "T002",
      "발생일": "2026-09-01",
      "이벤트유형": "퇴직급여입금",
      "금액": 150000000
    }
  ]
}
```

사용 가능한 이벤트 예시는 다음과 같다.

- 개인부담금 입금
- 퇴직급여 입금
- 상품 신규
- 상품 만기
- 매수
- 매도
- 상품변경
- 현금성자산 발생
- 디폴트옵션 적용
- 예약변경
- 계약이전 신청
- 계약이전 의사확인
- 연금개시
- 연금 인출
- 상담 발생
- 투자성향 변경

필요하면 새로운 이벤트 유형을 추가할 수 있다.

# 8. 외부금융정보

IRP 밖에서 확인되는 고객의 금융정보.

모든 고객에게 필요하지 않으며, Case에 실제로 영향을 주는 정보만 사용한다.

예:

```json
{
  "외부금융정보": {
    "ISA": [
      {
        "외부계좌ID": "EXT001",
        "금융기관": "신한은행",
        "평가금액": 80000000,
        "만기일": "2026-09-30",
        "정보확인일": "2026-09-10",
        "정보출처": "마이데이터",

        "자금사용계획": null,
        "IRP전환의향": null,
        "IRP전환예정금액": null
      }
    ],

    "타기관퇴직연금": [],

    "연금저축": [],

    "일반계좌퇴직급여": [],

    "기타금융자산": []
  }
}
```

활용 가능한 정보 예:

- 타행 ISA
- 타기관 IRP
- 연금저축
- 연금저축보험
- 일반통장으로 지급된 퇴직급여
- 다른 금융상품의 만기 예정
- 마이데이터 자산
- 기타 Case 판단에 필요한 외부정보

`자금사용계획`, `IRP전환의향` 등 상담에서 확인해야 하는 사항은 임의로 생성하지 않는다.

# 9. 디지털행동

KB스타뱅킹 등에서 확인할 수 있는 고객 행동이력.

예:

```json
{
  "디지털행동": [
    {
      "행동ID": "D001",
      "발생일시": "2026-09-08T19:42:00+09:00",
      "채널": "KB스타뱅킹",
      "행동유형": "조회",
      "조회분류": "퇴직연금상품",
      "조회대상": "ETF 상품"
    }
  ]
}
```

활용 예:

- ETF 조회
- TDF 조회
- 금리 조회
- 수익률 조회
- 상품변경 화면 진입
- 계약이전 조회
- 추가납입 조회
- 연금수령 조회

Digital Signal은 고객 의사를 확정하는 정보가 아니다.

```text
ETF 조회 ≠ ETF 매수 희망
계약이전 조회 ≠ 이전 의사 확정
수익률 조회 증가 ≠ 매도 의사
```

# 10. 상담이력

이전 상담에서 실제로 확인된 고객 발언이나 직원 메모.

```json
{
  "상담이력": [
    {
      "상담ID": "CRM001",
      "상담일": "2026-07-08",
      "상담채널": "영업점전화",
      "기록유형": "직원상담메모",

      "상담메모": "고객은 올해 추가 납입은 필요하지 않을 것으로 생각한다고 말함."
    }
  ]
}
```

상담이력에는 **BRIEF의 S4에 있는 예상 고객 반응을 넣지 않는다.**

예를 들어 S4에:

> “손실이 싫어서 그냥 두고 있었어요.”

라는 예상 반응이 있어도, 과거 CRM에 실제로 존재하는 설정이 아니라면 상담이력으로 만들지 않는다.

# 11. 파생데이터

RAW DATA를 바탕으로 계산하거나 Rule에 의해 생성되는 정보.

---

## 11.1 계산값

예:

```json
{
  "계산값": {
    "ISA만기까지남은일수": 19,
    "현금성대기일수": 119,
    "현금성자산비중": 16.9,
    "위험자산비중": 68.5
  }
}
```

활용 가능한 계산값 예:

- D-day
- 이벤트 발생 후 경과일
- 현금성 대기기간
- 자산별 비중
- 위험자산 비중
- 세액공제 잔여한도
- 전환기한
- 고객 상태 변화량

# 12. Badge

> **2026-09-21:** 실제 사용하는 뱃지 문구·색·정의는 [review/BADGE_CATALOG.md](../../review/BADGE_CATALOG.md)의 Dynamic Segment 39종이 기준이다. 아래 목록과 `뱃지코드` 예시는 초기 설계안이며 고객 JSON `signals`에는 쓰이지 않는다.

Badge는 고객의 최종 관리방향이 아니다.

직원이 고객 목록을 봤을 때 **왜 이 고객을 지금 봐야 하는지 빠르게 인지하기 위한 Fact / Signal**이다.

한 고객에게 화면상 노출되는 Badge는 대체로 1~3개를 기준으로 한다.

예:

```json
{
  "뱃지": [
    {
      "뱃지코드": "ISA_MATURITY",
      "구분": "이벤트",
      "표시문구": "타행 ISA 만기 D-19",
      "근거ID": [
        "EXT001"
      ]
    },

    {
      "뱃지코드": "ETF_VIEW",
      "구분": "디지털행동",
      "표시문구": "ETF 조회",
      "근거ID": [
        "D001"
      ]
    }
  ]
}
```

---

## 현재 Badge 후보

### Event / Timeline

- `ISA 만기 D-n`
- `ISA 전환기한 D-n`
- `정기예금 만기 D-n`
- `GIC 만기 D-n`
- `ELB 만기 D-n`
- `퇴직예정 D-n`
- `퇴직급여 입금 D+n`
- `퇴직급여 일반통장 입금 D+n`
- `퇴직급여 재입금기한 D-n`
- `계약이전 접수 D+n`
- `의사확인 대기`
- `연금개시 가능`
- `연금수령 중`
- `첫 입금 D+n`

### Account Attention

- `현금성 고비중`
- `현금성 장기대기`
- `원리금보장 100%`
- `DO 미등록`
- `DO 적용 D-n`
- `입금예정상품 미설정`
- `수익률 부진`
- `판매중단 펀드 보유`

# 14. NULL / 미확인 처리

Golden Case에서는 **모르는 것을 억지로 채우지 않는 것**이 중요하다.

예:

```json
{
  "자금사용계획": null,
  "IRP전환의향": null,
  "IRP전환예정금액": null
}
```

의미:

> 해당 정보가 아직 고객에게 확인되지 않음.

숫자 `0`과 `null`은 다르게 사용한다.

```text
0
= 확인 결과 실제 값이 0

null
= 아직 알 수 없음 / 확인되지 않음
```

# 17. Golden Case 제작 시 활용 원칙

본 Schema는 고객을 Schema에 맞추기 위한 것이 아니다.

**BRIEF가 정의한 고객 Story가 자연스럽게 존재할 수 있도록 DATA를 구성하기 위한 재료 목록**이다.

따라서 작업 순서는 다음과 같다.

```text
BRIEF 확인
↓
Case를 성립시키는 핵심 Evidence 추출
↓
화면직접표시데이터 구성
↓
최근 변화 / 외부정보 / Digital / CRM 구성
↓
실제 상품 연결
↓
계산값 생성
↓
Badge 생성
↓
BRIEF ↔ DATA 정합성 검증
```

Case에 필요하지 않은 필드를 억지로 채우지 않는다.

필요한 경우 본 문서에 없는 필드를 추가할 수 있으며, 반복적으로 활용되는 필드라면 이후 Schema에 정식 반영한다.

# 18. 현재 Schema의 설계 철학

좋은 고객 DATA는 단순히 정보가 많은 데이터가 아니다.

좋은 Golden Case DATA는:

1. 실제 고객처럼 현재 상태와 과거 변화가 자연스럽게 연결되고
2. 화면에 표시되는 숫자가 서로 맞으며
3. 상품정보가 실제 자료에 근거하고
4. Agent가 판단해야 할 내용은 정답으로 미리 넣지 않고
5. 이 DATA를 읽으면 왜 해당 BRIEF가 만들어졌는지 이해할 수 있는 데이터다.

즉,

**Customer DATA는 BRIEF의 정답을 저장하는 곳이 아니라, 그 BRIEF에 도달할 수 있는 Evidence를 저장하는 곳이다.**
