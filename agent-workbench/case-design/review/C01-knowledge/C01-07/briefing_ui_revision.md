# 오세훈 · S3 상품 메타정보 / S5 Hot Tip / 근거 자료 수정안

작성일: 2026-09-28 · 대상: C01-07 · 상태: **구현 전달용, 화면·Agent 미수정**

현재 오세훈 브리핑의 상품 펼침 영역을 메타정보 중심으로 바꾸고, S5에 실제 Hot Tip 한 건을 연결한다. 하단에는 초안·정제본 대신 해당 브리핑에서 참고한 원천 자료를 정리한다.

이 문서와 **[briefing_ui_revision.json](briefing_ui_revision.json)**을 함께 사용한다. JSON에는 적용할 값, 원문 발췌, 출처 연결, 기존 근거 맵의 변경 목록까지 준비되어 있다. 전체 지식을 다시 정제할 필요가 없다. 이 JSON은 새 런타임 입력 파일이 아니며, 구현자가 기존 수정 원본에 반영할 변경안이다.

기존 [briefing_trace_plan.md](briefing_trace_plan.md)의 네 단계 분석 근거 패널 기획을 이어간다. 그 문서의 전체 출력 보존 규칙 중 **S3 상품 펼침 표시, S5 팁 표시, 하단 출처·검토사항 표시**는 이 수정안이 우선한다. 고객 JSON, S1·S2·S4 문장, S3 관리방향 문장·상품 선택·순서, S5 단말 액션 네 개는 유지한다. 문장을 유지하는 섹션도 `sourceIds`는 원천 자료 ID로 교체한다.

## 1. 완성할 화면

### S3 — 추천상품 보기를 열면 상품 메타정보만

현재 펼침 카드의 `reason`, 긴 `notes`, `근거: GIC-003`, `근거: C01-07 오세훈` 행은 오세훈 화면에서 숨긴다. 상품명, 상품 유형, 위험등급이 있는 경우 그 등급, 기간별 금리·수익률, 자료 기준만 표시한다. 원인 설명은 위 관리방향과 분석 근거 패널에서 확인한다.

```text
한화생명 GIC (2026년 9월 특별제공안)
이율보증형보험(GIC) · 원리금보장

기간          1년       2년       3년       5년
표시금리     4.00%     3.48%     4.48%     3.54%
2026.09 자료 기준
```

기간별 값은 작은 표 또는 같은 폭의 메타정보 행으로 표시한다. 금리에는 양수 `+`를 붙이지 않고 소수 둘째 자리까지 표시한다. 기준 문구는 카드 안에서 한 번만 표시해 반복을 줄인다. 유효한 0은 유지하고, 음수 수익률 부호도 유지한다.

| 상품 | 유형·위험 | 표시할 수치 | 기준 표시 |
|---|---|---|---|
| SBI저축은행 퇴직연금 정기예금 | 저축은행 정기예금 · 원리금보장 | 1년 3.85% / 2년 3.95% / 3년 3.95% | 2026.09 자료 기준; 적용기간 2026.09.01~09.30 |
| 한화내일받는단기국공채증권자투자신탁(채권)C-RPE(퇴직연금) | 국내채권 · 단기국공채 · 실적배당형 / 6등급 · 매우낮은위험 | **누적수익률** 6개월 1.35% / 1년 2.53% / 3년 10.18% | **기준일 미표기** |
| 한화생명 GIC (2026년 9월 특별제공안) | 이율보증형보험(GIC) · 원리금보장 | 1년 4.00% / 2년 3.48% / 3년 4.48% / 5년 3.54% | 2026.09 자료 기준 |

수치는 `SRC-099 PRODUCT_MASTER`의 해당 세 레코드에서 확인했다. 연결된 원천 제목은 확인했지만 원천 상품 파일/PDF 본문은 미확보다. 따라서 수치의 확인 범위는 **로컬 마스터의 자료값**이다. 현재 판매 가능성이나 거래일 금리를 새로 확인한 것은 아니다.

- SBI의 3·6개월 값은 중도해지 참고율이다. 가입 기간으로 추가하지 않는다.
- GIC는 자료에 정확한 적용 시작일·종료일이 없어 월 정보만 보존한다. 이름도 현행 특별제공안 명칭을 유지한다.
- 펀드 수익률은 원문 기준일이 없다. `asOf`를 고객 기준일이나 마스터 작성일로 채우지 않는다. 기간 누적수익률을 연환산하거나 “현재 수익률”로 바꾸지 않는다.
- 예금·GIC의 9월 값을 고객의 10월 만기 후 적용금리로 약속하지 않는다. 날짜는 메타정보로 계속 보인다.
- 분석 근거의 상품 묶음명 **연금사업부 9월 추천상품**은 유지한다. FND-004가 공식 월간 추천 클래스라는 새 사실을 만들지는 않는다(`monthly_recommended=false`).

### S5 — 관련 Hot Tip 한 건 + 기존 실행 화면

```text
Hot Tip · 2025.02.27
IRP 연금 지급 절차
연금개시 준비서류와 세액 미공제 한도 등록, 연금지급 화면으로
이어지는 처리 흐름을 정리한 현장 사례입니다.
                                           [원문 보기 ↗]

04-12-642  적립금및수익률조회
04-12-17A  NEW 퇴직연금상품조회
06-12-611  보유상품변경
02-12-221  개인형IRP 연금지급

상담 후 확인
계속 운용 / 연금수령 검토 중 고객의 선택을 기록하고,
만기 후 실제 재운용 또는 연금지급 여부를 확인합니다.
```

위 예시는 배치 기준이다. 액션의 기존 설명·버튼·열기 동작은 유지한다. `상담 후 확인`은 삭제하지 않고 액션 아래의 짧은 일반 안내로 옮긴다. 강조된 Hot Tip 카드는 정확히 한 개다.

- 선정 자료: `SRC-049`, 글번호 `199404`, 원천 제목 `irp 연금 지급 절차`, 작성일 `2025-02-27`.
- 선택 이유: 오세훈의 현재 브리핑에 있는 연금수령 검토와 `02-12-221` 연결을 직접 보완한다.
- 준비서류와 처리 순서를 소개하는 **현장 사례**로 요약한다. 이 글에서 현재 제도 요건이나 모든 거래의 의무 절차를 새로 도출하지 않는다.
- 원문 링크는 게시글에 기록된 실제 LXP 주소를 사용한다. 로컬 자료에서 URL을 확인했으며 로그인 후 접속은 미검증이다. 링크는 안전한 HTTPS 새 창 열기를 사용한다.
- RAW는 해당 MD 34~40행의 실제 문자열 7행을 그대로 사용한다. 원문에 `0612622`가 있어도 새 실행 버튼을 추가하지 않는다.

JSON에는 RAW 전문과 해시가 들어 있다. 원문에는 준비서류, 세액 미공제 한도 등록, 연금지급이 순서대로 나온다. 글의 다른 문단에 있는 세금·계약이전 관련 일반화는 이번 카드에 포함하지 않는다.

## 2. 하단 근거 자료와 기존 분석 근거를 연결

하단 제목은 **근거 자료**로 바꾸고 처음에는 접힌 상태를 유지한다. 펼치면 아래 원천 제목만 행으로 표시한다. 파일 경로, `.md`, 버전·행 번호, `PRODUCT_MASTER`, `runtime_verified`, 정제본·초안 이름은 표시하지 않는다.

| irp 연금 지급 절차 | H-PENSION | S5 Hot Tip |

같은 문서를 여러 지식 카드가 사용하더라도 출처 행은 하나다. 제목 선택 시 기존 **분석 근거 패널**의 관련 지식으로 바로 이동한다. 그 안에서 짧은 요약 → 확인한 원문 몇 줄 → 실제 반영 위치를 본다. 별도 로그 목록이나 중첩 모달을 만들지 않는다.

- `guide-irp`처럼 여러 카드가 연결된 자료는 해당 카드만 선택할 수 있는 짧은 목록을 보인다. 실제 사용 문장은 기존 `bindings`에서 읽는다.
- RAW가 있는 자료는 기존 검증된 발췌를 재사용한다. Hot Tip 발췌 한 개만 추가한다.
- 상품 원천 세 개는 **제목과 요약·사용 위치**를 보여준다. 원천 본문을 확보하지 못했으므로 RAW/원문 열기 버튼과 가짜 PDF 링크를 만들지 않는다. 마스터의 정리문을 원천 직접 인용으로 바꾸지 않는다.
- `analysis_trace`가 없는 응답에서도 브리핑·출처 제목·확인된 Hot Tip 링크는 정상 표시한다. 연결할 근거가 없으면 패널 이동 버튼을 숨긴다.
- 고객 변경·응답 교체 시 선택 출처를 초기화하고, 이전 고객의 자료가 남지 않도록 기존 ticket·취소 처리를 유지한다. 패널 닫기와 키보드 포커스 복귀도 기존 동작을 따른다.

`reviewNotes`는 원본의 내부 검토 기록으로 남긴다. **오세훈 고객 화면에서는 이 목록과 ‘검토사항’ 제목을 렌더링하지 않는다.** 화면에서 숨겼다고 검증 상태를 `ready`로 바꾸거나 자료의 불확실성을 지우지 않는다. 금리 기준월과 펀드의 기준일 누락은 상품 메타정보에 계속 표시한다.

## 3. 준비된 데이터 적용 방법

`briefing_ui_revision.json`은 다음 내용을 담는다.

| 항목 | 내용 |
|---|---|
| `baseline` | 기획 당시 고객/브리핑 원본 경로와 SHA256. 현재 값이 달라지면 변경 원인을 먼저 대조 |
| `briefing_patch` | C01-07 원본에 적용할 JSON Patch 21개. 메타정보·팁·출처만 변경 |
| `product_provenance` | 세 상품의 마스터 위치, 원천 제목·참조, 수치가 나온 필드 |
| `evidence_revision` | 새 Hot Tip 카드·RAW, 출처 ID 맵, 제거/이동/추가할 문장 binding |
| `source_catalog_map` | 원천 9개와 지식 카드 11개의 연결 |
| `frontend_policy` | 이번 고객의 메타정보 표시·팁 배치·출처 펼침 기준. 응답으로 보내는 UI 스키마가 아님 |
| `contract_changes` | 기존 스키마에서 확장할 최소 필드 |

현재 `reason`, `notes`는 데이터에서 지우지 않는다. 상품 펼침에서만 숨긴다. 다만 패널의 **화면 반영 문장** 목록에는 숨겨진 상품 설명을 넣지 않도록 해당 9개 `binding`을 제거한다. 지식 카드의 `summary`·`application`은 고객 적용 근거로 계속 사용한다.

출처 ID 변경은 `briefing_patch`에 포함했다. `refined`, `draft`를 지우기만 하면 참조가 깨지므로 모든 `sourceIds`를 같이 반영한다. S1은 기존 유효한 고객 `dataRefs`를 근거로 유지한다. S3의 기존 TDF·ETF 유지 판단을 GIC 원천 문장의 직접 결론으로 연결하지 않는다.

### 기존 briefing_evidence.json의 후속 갱신

1. 10개 기존 지식 카드의 `source_id`를 제공된 맵대로 추가하고 `H-PENSION`을 추가한다. 기존 RAW와 사실 맵은 재작성하지 않는다.
2. 숨긴 상품 `reason`·`notes`에 해당하는 `binding` 9개를 제거한다.
3. 기존 후속관리 `B39`, `B40`의 경로를 `/s5/tips/1/...`로 바꾼다. `J-FOLLOWUP`은 유지한다.
4. 제공된 `B53`~`B58` 여섯 개를 추가한다. 상품 유형 3개, 펀드 위험등급, Hot Tip 제목·본문이다.
5. 모든 카드의 `used_by`는 최종 `bindings[].evidence_ids`에서 다시 계산한다. `workflow.followup`도 `/s5/tips/1`로 이동한다. workflow 지식 묶음에 H-PENSION을 넣고 제목은 `단말 업무 · Hot Tip`으로 한다.
6. 완성 후 예상 수: 단계 4 / 고객 필드 16 / 지식 카드 11 / RAW 보유 카드 8 / RAW 발췌 12 / binding 49. 삭제된 binding ID를 억지로 다시 채우거나 재번호하지 않는다.
7. 현재 원본 변경을 검토한 후 브리핑 baseline 해시를 갱신한다. 고객 해시는 유지한다. `preserve_briefing=true`는 **승인된 새 baseline을 이후에도 보존한다**는 의미로 유지한다. 해시/`expected_text`/RAW 검증을 제거해 빌드를 통과시키지 않는다.

숫자 `metrics`를 문자열 전용 `binding`에 강제로 넣지 않는다. 상품별 `sourceIds`와 출처 카드로 연결하고, 수치·기간·기준은 구현 검사에서 준비된 값과 대조한다. 자료 작성일은 게시일이며 실행 타임스탬프가 아니다. 분석 근거의 네 단계·실제 관측 시각·`llm_calls=0`은 유지한다.

## 4. 프론트와 Agent를 함께 맞출 범위

**프론트 표시 변경 + C01 원본/근거 맵 갱신 + 작은 응답 계약 확장**이 필요하다. 새 LLM 생성 로직은 필요하지 않다. 현재 고정 Agent의 반환 방식은 유지하고, 새 필드를 누락하지 않도록 연결한다.

| 파일/영역 | 구현할 내용 |
|---|---|
| `active/briefing-json/C01-07.json` | 제공된 patch 반영. 고객 JSON은 유지 |
| `review/C01-knowledge/C01-07/briefing_evidence.json` | 위 근거 맵 후속 갱신 |
| `frontend/src/briefing/briefing-contract.js` | 아래 metrics·tip 필드 허용, 정규화와 의미 검증 |
| `frontend/src/briefing/fabrix-briefing-contract.js` | 선택 `knowledge_cards[].source_id`와 같은 briefing의 출처 존재 검증 |
| `integration/contracts/AGENT_FRONTEND_CONTRACT.md` | §4.1 TIP, §4.2 지표, §4.4 근거 카드의 실제 계약과 일치 |
| `pensionBriefingView.js` / `pensionBriefingAdapter.js` | 선택 고객 문맥으로 C01 표시 정책 전달. 다른 고객의 기존 표시 유지 |

표에서 축약한 `active/`, `review/`는 `agent-workbench/case-design/` 하위이고, 프론트 파일명은 `frontend/src/briefing/` 하위다.

최소 계약 변경:

- **`metrics[].asOf`**: 키는 계속 필수. `kind=return`일 때만 명시적인 `null`을 허용하고 “기준일 미표기”로 렌더링한다. `kind=rate`는 공백 아닌 문자열이 필요하다. 기존 날짜 문자열 응답은 그대로 유효하다. 현재 작은 JSON Schema 검증기가 지원하지 않는 조건부 문법을 넣기보다 기존 의미 검증 경로도 함께 맞춘다. `null 기준`이 화면에 나오지 않게 한다.
- **`s5.tips[].kind?`**: `hot_tip` / `follow_up`. 기존 kind 없는 tip은 기존 방식으로 렌더링한다.
- **`s5.tips[].publishedAt?`**: `YYYY-MM-DD` 게시일. 원문 링크는 같은 tip의 `sourceIds → sources.url`에서 찾고 중복 URL 필드를 추가하지 않는다.
- **`analysis_trace.knowledge_cards[].source_id?`**: 선택 문자열. 있으면 `briefing.sources[].id`와 연결을 검증한다. 새 C01 맵의 11개 카드는 모두 포함한다. strict 객체 helper가 모든 키를 기본 필수로 만드는 점을 확인해 실제로 선택 필드로 선언한다.

`customer-briefing-output.v2`와 FabriX envelope는 유지한다. 입력 허용 범위를 확장하는 것이므로 기존 payload는 새 코드에서 계속 유효해야 한다. 다만 기존 프론트의 엄격한 스키마는 새 tip 필드를 거부할 수 있으므로 **프론트와 Agent 생성 계약·데이터를 한 반입 묶음으로 맞춘다.** 새 Agent만 먼저 배포해도 된다고 가정하지 않는다.

기존 분석 근거의 고객 `snapshot` 등 현재 구현에 추가된 필드는 그대로 보존한다. 이 문서의 표를 응답 전체를 다시 만드는 명세로 사용하지 않는다. 이번 작업과 동시에 진행된 화면·Agent 변경도 먼저 확인하고 필요한 부분만 수정한다.

사내 구현은 기존 Vanilla JS/Starroot 수명주기와 `#pensionAgentDemo` CSS 범위를 따른다. React·CDN·DOMContentLoaded, 새 패키지, 외부 상품 실시간 조회는 추가하지 않는다. 신규 Python 모듈은 필요하지 않으며 기존 flat import·LLM 인터페이스도 유지한다. Agent 수정 전 `docs/platform/02-AGENT_DEVELOPMENT.md`의 해당 부분을 읽는다.

## 5. 구현 완료 판정

1. 오세훈에서 세 옵션을 각각 펼치면 상품명·유형·필요한 위험등급·수치·기준만 나온다. 긴 설명/검토 문장/중복 근거 배지가 사라진다. 다른 고객의 상품 카드는 기존대로다.
2. 준비된 금리 7개와 누적수익률 3개가 기간·기준과 함께 정확하다. 펀드의 “기준일 미표기”, SBI 적용기간, GIC 기준월이 보인다.
3. S5 Hot Tip 강조 카드가 한 개이며 원문 링크가 준비된 주소와 같다. 단말 네 개와 기존 설명을 보존하고 후속관리 문구가 액션 아래로 이동한다.
4. 출처가 원천 제목 9개로 정리된다. `refined`/`draft` 참조가 남지 않고 reviewNotes는 이 고객 화면에서 숨겨진다.
5. 출처 선택 → 기존 분석 근거 패널에서 사용 위치와 RAW를 확인한다. Hot Tip RAW는 7행 원문과 같고 상품 세 자료에는 RAW 버튼이 없다.
6. S1·S2·S4 및 S3 관리방향 문장, 고객 JSON, 액션 값이 유지된다. 이전 고객/이전 응답의 출처가 잔류하지 않는다. 기존 trace 없는 응답도 표시된다.
7. 구조 검증과 별도로 위 표시·출처·수치 일치를 확인한다. `asOf=null`인 return 허용, rate 거부, 알 수 없는 source_id 거부, 기존 필드만 있는 응답 허용을 검사한다.

구현 후 루트에서 `node tools/briefing/build.js`, `node tools/briefing/check.js`를 실행한다. Agent를 수정하므로 `node tools/briefing/check.js --agent`도 실행하고 HTTP/SSE 검사 SKIP은 그대로 보고한다. 브라우저에서 실제 펼침·팁·출처 이동을 확인한다. 전체 고객은 회귀 검증에서만 사용한다.

생성 반입본 `frontend/briefing-fabrix/`, `agent/briefing_data.json`, 생성 계약/예시는 빌드로만 갱신한다. 이 계획 JSON을 런타임에서 새로 fetch하거나 빌드 입력으로 등록하지 않는다. 요청 없는 commit/push/사내 배포는 하지 않는다.

기획 자료 작성 시 검증: 변경안 21개를 메모리에서만 적용해 원천 수치 10개, 출처 참조 9개, 최종 binding 49개와 RAW 발췌 12개의 원문·해시 일치를 확인했다. 보존 대상 문장·액션도 대조했다. 현재 코드의 `build.js`와 `check.js`는 통과했다. 이는 **현재 구현의 회귀 검사**이며 이 수정안의 화면 완성이나 사내 접속 검증을 뜻하지 않는다. 이번 작업에서는 Agent 코드를 수정하지 않아 `--agent`는 실행하지 않았다.
