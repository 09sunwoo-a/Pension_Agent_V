# C01-07 오세훈 · 브리핑 근거 패널 구현 기준

작성일: 2026-09-28 · 고객 데이터 기준일: 2026-09-29

> 후속 수정안: **[S3 메타정보·S5 Hot Tip·근거 자료 정리](briefing_ui_revision.md)**와 [적용할 데이터](briefing_ui_revision.json). 이 문서의 전체 출력 보존 규칙 중 해당 세 영역은 후속 수정안이 우선한다. 네 단계 근거 패널과 나머지 문장 보존 원칙은 유지한다. 후속 파일은 구현 전달용이며 현재 런타임 입력에는 아직 적용하지 않았다.

이 문서는 사용자와 확정한 화면·로그·출처 표시 기획이다. 함께 있는 **[briefing_evidence.json](briefing_evidence.json)**에는 이미 정제한 고객 필드 맵, 표시 문구, 실제 원문 발췌, 현재 브리핑 문장과의 연결이 들어 있다. 구현자는 지식 선정·요약·매핑을 다시 작성하지 않고 이 자료를 코드에 연결한다.

**이번에 준비한 것은 구현용 자료다. 프론트와 Python에 연결된 상태는 아니다.** 현재 고객 Agent는 LLM 없는 고정 브리핑 반환이다. 이번 구현은 그 결과에 구성 근거를 덧붙이는 범위이며, 새 Gemma 호출은 포함하지 않는다.

## 1. 읽을 파일과 고정 기준

1. 이 문서와 `briefing_evidence.json`.
2. [오세훈 고객 JSON](../../../active/display-data/C01-07.json), [현재 화면용 브리핑 JSON](../../../active/briefing-json/C01-07.json).
3. 루트 README 작업별 표와 AGENTS.md를 따라 필요한 구현 파일만 읽는다.

기존 `briefing_draft.md`와 `knowledge_pack.md`의 긴 본문은 과거 검토 자료다. 현재 JSON과 다른 초안 문장, 과거 고객 값, 추가 상품·상담 분기를 화면으로 복원하지 않는다. 지식 원천은 JSON `provenance`로 직접 찾아간다. 다른 고객 자료와 지식 전체를 다시 읽을 필요는 없다.

고정할 현재 결과:

- S1: 핵심 사실 3문장.
- S2: 관리방향·왜 지금·확인 질문 3개.
- S3: 현재 옵션 3개와 상품 3개. 문장·상품·순서를 유지한다.
- S4: 현재 도입 문장, 예상 반응 3개, 유의사항.
- S5: `04-12-642`, `04-12-17A`, `06-12-611`, `02-12-221` 네 액션과 별도 `상담 후 확인` 팁.
- 브리핑 문장은 런타임에 같은 응답의 `briefing`에서 읽는다. JSON 맵의 `expected_text`는 현재 원본 대조용이며 새 문장 생성이나 두 번째 수정 원본이 아니다.

## 2. 핵심 화면: 네 단계만 기본 노출

오세훈 고객 상세의 브리핑 제목 근처에 작은 **[분석 근거]** 버튼을 둔다. 누르면 해당 고객의 현재 브리핑 근거를 바로 연다. 메인 처리 이력 목록을 경유하지 않는다.

```text
오세훈 · 브리핑 분석 근거                         [닫기]
요청 시각 · 응답 시각

▸ 고객 상황 요약                       [처리 시각]
  7,040만원 만기 · 연금 미개시 · 운용 지속 의향

▸ 관리포인트                           [처리 시각]
  재운용 전 현재 연금수령 계획 확인

▸ 참고한 업무·상품 지식                 [처리 시각]
  만기 관리 · 상품 · 상담화법 · 단말 업무

▸ 브리핑 반영                          [처리 시각]
  확인한 사실과 근거를 S1~S5에 연결
```

- 네 단계 모두 처음에는 접힘. 기본적으로 한 단계만 펼친다.
- 시간은 실제 요청/응답 및 Agent의 근거 구성 작업에서 관측한 값. 자료에 적힌 기준일을 실행 시각으로 쓰지 않는다.
- 패널 이름은 `분석 근거`. 고정 응답의 근거 구성을 실제 LLM 문장 생성 기록으로 표시하지 않는다.
- 요청 ID·SSE·revision·deployment·token·validation·렌더링을 별도 기본 로그 행으로 나열하지 않는다.
- UI에 DEMO/MOCK 등의 문구나 정제 이력을 붙이지 않는다. 실제 관측·자료 발췌·사전 작성한 고객 적용 판단의 구분은 내부 데이터에 보존한다.
- 중첩 모달은 만들지 않는다. 원문과 사용 위치는 선택한 카드 안에서 함께 확인한다.
- 원문은 기본 최대 8행을 보이고 필요하면 같은 영역에서 더 보기. 전체 문서를 싣지 않는다.
- 짧은 문장이 즉시 완성돼도 인위적으로 호출·지연·타이핑 로그를 만들어 늘리지 않는다.

### 단계별 펼침 내용

| 단계 ID | 펼쳤을 때 | 사용 데이터 |
|---|---|---|
| `customer_summary` | 사용한 JSON 키·값 → 현재 S1 세 문장 | `facts`, S1 `bindings` |
| `management_focus` | 사실 세 가지 → 짧은 관리포인트 → 현재 S2 | `J-PLAN`, `J-SPLIT`, S2 `bindings` |
| `knowledge_selection` | 네 묶음에서 지식 카드 선택 → 출처 제목·요약·RAW·반영 문장 | `presentation.groups`, `knowledge_cards` |
| `briefing_binding` | S1~S5의 핵심 문장과 근거 연결, 기존 브리핑으로 이동/강조 | `bindings` |

S1~S5 전문을 패널에 다시 복제하지 않는다. 발표자는 상황 요약과 관리포인트를 설명한 뒤 지식 카드 하나만 열어도 된다.

필드 경로와 기준 값은 JSON에 준비되어 있다. 실제 응답을 구성할 때는 검증된 요청의 `customer_data`에서 값을 읽는다. `expected_values`를 런타임 값으로 복사하지 않는다.

- 만기 D-10은 `as_of_date=2026-09-29`와 만기일의 차이다. 서버의 오늘 날짜 기준으로 다시 해석하지 않는다.
- 보유행 H002와 만기 이벤트의 관련 ID·금액을 대조한다. 만기 이벤트의 금액을 다른 상품에 연결하지 않는다.
- 연금수령 가능은 입력 데이터의 상태다. 새 법률 판정이나 고객의 개시 동의를 뜻하지 않는다.
- 과거 상담 의향은 현재 의향으로 확정하지 않는다.
- 납입·세액공제·이탈징후 등 이번 브리핑에 쓰지 않는 정보로 새 관리포인트를 추가하지 않는다. 과거 pack의 900만원/0원과 달리 현재 납입/잔여한도는 200만원/700만원이다.

### 관리포인트 표시 문구

`J-PLAN`:

> 만기자금을 재운용하기 전에, 지난 상담 이후 연금수령 계획이 달라졌는지 확인할 필요가 있습니다.

`J-SPLIT`:

> 연금수령을 검토한다면 필요한 시점과 금액을 확인하고, 받을 자금과 계속 운용할 자금을 구분합니다.

연결되는 현재 S2:

> 만기자금을 다시 운용하기 전에 **연금수령 계획이 달라졌는지 확인하고, 받을 자금과 계속 운용할 자금을 구분**합니다.

이 판단 요약은 고객 사례에 적용한 편집 내용이다. 지식 원문에 오세훈의 결론이 적혀 있던 것처럼 인용하지 않는다. 실제 LLM 사고 토큰이나 실행 이력으로 표시하지 않는다.

### 출처 표시와 RAW 규칙

- 출처에는 `source_title`만 표시한다. 예: `개인형IRP_마케팅_보물지도_Vol1`.
- 상품 검색 묶음의 화면 이름은 **연금사업부 9월 추천상품**이다. 원본 파일명이나 공식 추천 여부를 일괄 변경하는 의미는 아니다.
- 상품 카드의 제목은 마스터의 원천 목록에서 확인했다. 세 원 상품파일은 현재 저장소에서 찾지 못했으므로 `raw_excerpts=[]`로 준비했다. 이 카드에는 제목·참고 내용·반영 위치만 표시한다.
- 상품 마스터를 해당 원 상품파일의 RAW로 가장하지 않는다. 공식 월간 추천으로 확인되지 않은 클래스를 월간 추천 확정으로 바꾸지 않는다.
- 나머지 카드의 RAW 11개는 실제 `knowledge/corpus` MD에서 줄 단위로 발췌했다. MD에 들어 있는 문법·오탈자·옛 표현까지 그대로 보존한다. PDF 자체 대조를 완료했다는 뜻은 아니다.
- 원문 제목·원문 조각·요약·고객 적용을 구분한다. 기본 화면에는 제목과 요약, 펼친 카드에는 RAW와 반영 문장을 함께 보여준다.
- `source_path`, 행 범위, 발췌 SHA-256은 내부 검증용이다. 화면 경로/행 번호 표시는 하지 않는다.
- 텍스트는 `textContent` 또는 동등한 안전한 렌더링을 사용한다. 원문 안의 `<u>` 등을 임의 HTML로 실행하지 않는다.
- 원문을 불연속으로 잘라 한 문장처럼 붙이지 않는다. JSON의 각 발췌 블록을 구분해서 표시한다.

### RAW 표시 예시: K-PENSION

출처: **개인형IRP_마케팅_보물지도_Vol1**

```text
### 연금수령방식 3가지

| 구 분 | 수령기간 | 수령금액 | 비 고 |
| --- | --- | --- | --- |
| 기간지정 | 고정 | 변동 | 방식 간 변경 가능 |
| 금액지정 | 변동 | 고정 | |
| 자유인출 | 최소 연금수령기간 이상 | 고객 지정 | |
```

한 줄 요약: 기간지정·금액지정·자유인출 방식에 따라 수령기간과 금액을 정하는 구조가 다르다.

반영: `S2 고객과 확인` → **연금을 시작한다면 언제부터 얼마 정도 받을지**.

## 5. 섹션별 연결에서 지켜야 할 점

### S3

| 현재 상품 | 정제한 연결 이유 |
|---|---|
| SBI저축은행 퇴직연금 정기예금 | 현재 SBI 예금의 같은 역할 재운용 조건 비교. |
| 한화내일받는단기국공채 C-RPE | 손실 가능성을 이해한 단기 운용 부분의 비교 후보. |
| 한화생명 GIC | 가까운 지급에 쓰지 않을 장기 잔액의 구조 비교. |

- 현재 원문 상품명은 브리핑의 `name`에서 읽는다. 카드 제목은 탐색용 축약명이다.
- 원문에 없는 10월 금리·정산일·실제 판매가능 여부를 생성하지 않는다.
- 옵션3의 기존 TDF·ETF 유지 점검 문장에는 `J-RETAIN`과 고객 보유사실을 연결한다. `P-GIC003`은 펼친 상품 카드의 별도 비교 근거다. GIC를 기존 TDF·ETF와 동일시하거나 교체 지시로 연결하지 않는다.

### S4

- 도입 문장: 만기예금 + 과거 상담 메모 + 계획 재확인 + 만기 안내 화법.
- 계속 운용 반응: `T-MATURITY`와 상품 조건 비교.
- 연금수령 고민 반응: S2의 `J-SPLIT`과 `K-PENSION` 재사용.
- 결정 보류 반응: `T-DEFER`와 `T-EXPERT`.
- 반응 세 가지는 상담 준비용 가정이다. 실제 발화나 동의로 기록하지 않는다.
- 원문에 있는 문자 발송, 한 달 전 예약 등의 표현을 새 실행 약속으로 추가하지 않는다. 현재 브리핑 문장을 유지한다.

### S5

```text
공통: 04-12-642 적립금및수익률조회
계속 운용: 04-12-17A NEW 퇴직연금상품조회 → 필요 시 06-12-611 보유상품변경
연금수령 선택: 02-12-221 개인형IRP 연금지급
후속관리: 현재의 '상담 후 확인' 팁
```

네 화면을 모두 실행한 순서로 기록하지 않는다. `J-FOLLOWUP`은 현재 브리핑의 후속관리 문구이며, 단말 원문에서 확인한 필수 절차로 승격하지 않는다.

## 6. JSON 맵 사용 방법

| 키 | 구현에서의 사용 |
|---|---|
| `baseline` | 현재 고객/브리핑 원본 경로와 정규화 JSON 해시. 작업 중 원본이 달라졌는지 확인 |
| `presentation.steps` | 네 단계 제목·요약·펼침 범위. 타임스탬프는 미포함 |
| `presentation.groups` | 지식 카드 네 묶음의 순서와 이름 |
| `facts` | 요청 고객 JSON에서 읽을 정확한 포인터 16개와 대조용 값 |
| `judgments` | 사전 작성한 고객 적용 판단 4개. 실제 LLM 출력이 아님 |
| `knowledge_cards` | 표시 제목·요약·고객 적용·RAW·내부 출처·역방향 사용 위치 |
| `bindings` | 현재 브리핑의 문자열 필드 52개와 사실/지식/판단의 연결 |
| `workflow` | 공통·계속 운용·연금수령·후속관리 분기 |

각 `binding.target`은 `data.briefing` 기준 JSON Pointer다. `/s3/options/0/products/0/reason`과 같은 경로를 같은 응답의 브리핑에서 해석한다. `fact.data_refs`는 요청의 `customer_data` 기준이다. 모든 경로는 현재 원본과 대조해 준비했다.

현재 문자열을 기대값과 대조하되, 일부 `binding`이 사전 작성된 적용 판단 또는 고객 가정임을 `role`로 구분한다. 모든 문장이 외부 업무문서의 직접 인용은 아니다.

최상위 RAW 카드 수 7개, RAW 조각 11개, 지식 카드 10개는 내부 데이터 개수다. 기본 패널에 이 수만큼 로그 행을 만들지 않는다.

## 7. Agent → 응답 → 프론트 구현

### 수정 경로

| 위치 | 해야 할 변경 |
|---|---|
| `tools/briefing/build.js` | 이 근거 JSON을 읽고 오세훈 배포 자료에 포함. 원본 MD/JSON을 덮어쓰지 않음 |
| `agent/briefing.py` | 검증된 C01-07 요청에서 사용 사실 추출, 준비된 지식 선택, 현재 브리핑 포인터 연결, 실제 시각 기록 |
| `agent/main.py` | Pydantic 응답에 선택적 근거 필드 허용 |
| `frontend/src/briefing/fabrix-briefing-contract.js` | 선택적 `data.analysis_trace` 스키마·반환값·검증 연결 |
| `frontend/src/briefing/briefing-contract.js` | S1~S5 구조 유지; 공통 검증 도우미와 필요한 참조 검사 검토 |
| `pensionFabrix.js`, `pensionBriefingAdapter.js`, `pensionBriefingStore.js` | 검증된 같은 요청의 브리핑과 근거를 원자적으로 저장·교체 |
| `pensionExecutionTracePanel.js` 및 필요한 작은 고객용 모듈 | 공통 패널 외형 재사용, 고객 문맥·간결한 네 단계·카드 펼침 구현 |
| `mnPensionAgentDemo.html`, `pensionAgentDemo.css` | 고객 브리핑 버튼·범위 제한 스타일 |
| `integration/contracts/AGENT_FRONTEND_CONTRACT.md` | 구현한 선택 필드와 호환성 기록 |

테이블의 짧은 프론트 파일명은 모두 `frontend/src/briefing/` 아래다. 응답 필드를 추가하기 전에 계약 문서와 두 계약 JS를 함께 읽는다. 현재 API/Pydantic은 추가 필드를 금지하므로 Python만 수정하면 실패한다.

### 권장 연결 방식

1. 근거 원본 JSON을 빌드에서 읽고 검증하여 기존 Agent 배포 묶음의 C01-07 레코드에 포함한다. 브라우저에 별도 지식 JSON fetch를 추가하지 않는다.
2. Agent는 기존 입력·스냅샷 검사를 유지한 뒤 사실의 값을 요청에서 읽고 근거 맵의 연결을 해석한다.
3. 기존 `data.briefing`과 선택적 `data.analysis_trace`를 하나의 `answer`에 담는다. 현재 단일 answer + EOF 흐름을 유지한다.
4. trace에는 네 단계의 실제 처리 시각, 사용한 사실 값, 지식 카드, 브리핑 연결을 담는다. 검증용 `expected_*`와 전체 경로 등 필요한 범위를 넘어선 내부 작성 메타데이터를 그대로 전송하지 않는다.
5. 프론트는 응답 검증 후 같은 ticket으로 브리핑과 trace를 함께 저장한다. 저장된 trace로 패널을 렌더링한다.

논리 응답의 위치:

```text
data
├ briefing             기존 S1~S5, 변경 없음
└ analysis_trace       선택 필드, C01-07에만 제공
  ├ mode               fixed_briefing_evidence
  ├ origin             agent_observed
  ├ started_at / ended_at
  ├ steps              네 업무 단계; 실제 근거 구성 시각
  ├ facts              요청에서 추출한 필요한 값
  ├ judgments          case_authored 출처 구분 유지
  ├ knowledge_cards    제목·내용·원문 조각
  └ bindings           위 자료와 동일 briefing의 target 연결
```

이는 아직 기존 API에 존재하지 않는 필드다. 구현자가 공유 계약으로 정식 정의한다. 정적 JSON의 작성일을 런타임 시간으로 쓰거나 `llm_calls=0`을 실제 LLM 호출로 바꾸지 않는다. 기존 고객 스냅샷이 바뀌면 현재 Agent의 불일치 거부 동작을 유지한다.

### 요청·캐시·오류

- request_id·case_id·customer_id·as_of_date 일치와 기존 EOF 검증을 유지한다.
- optional trace 없는 기존 응답·다른 고객은 기존 브리핑만 정상 표시한다.
- 오세훈 trace를 다른 고객에게 복제하지 않는다. 고객 전용 버튼은 유효한 trace가 있는 오세훈 브리핑에서 제공한다.
- 패널 열기·다시 고객 선택은 캐시를 사용한다. 명시적 재요청 성공 때만 브리핑/근거를 함께 교체한다.
- 실패·취소·오래된 응답은 새 trace 완료를 만들지 않는다. 이전 결과를 유지하면 이전 브리핑과 이전 trace를 함께 유지한다.
- 고객 변경·목록 복귀 시 패널을 닫고, 종료 시 이벤트·상태를 정리한다.
- Front 요청·응답 시각과 Agent 내부 시각을 구분한다. 서로 다른 시계 차이를 실행시간으로 해석하지 않는다.
- trace의 잘못된 ID/포인터/중복 연결은 계약·의미 검사에서 처리하고 다른 응답의 근거와 조용히 섞지 않는다.

## 8. 기존 메인 처리 이력 간소화

기존 패널은 부점 브리핑 생성 12단계 + 조회 7단계 등을 자세히 나열한다. 기록을 업무 단위로 묶어 기본 노출을 줄인다.

| 기록 종류 | 기본 노출 |
|---|---|
| 오늘의 부점 브리핑 | 고객 변화 확인 → 관리대상 선정 → 브리핑 구성 |
| 부점 AI 검색 | 검색조건 해석 → 고객 조회 → 결과 반영 |
| 엑셀 | 추출대상 확인 → 파일 생성·다운로드 요청 |

기존 내부 기록은 유지하고 대표 결과를 묶어 표시한다. 기록의 실제/시연 출처 구분, 검색 조건·인원·정렬, 엑셀 스냅샷은 바꾸지 않는다. 부점 데이터는 현재 수를 유지하며 1,392명으로 늘리지 않는다. 다운로드 요청을 디스크 저장 완료로 기록하지 않는다.

## 9. 환경과 검증 기준

- Vanilla JS, Starroot `PG_<파일코드>.onParam`/`onBeforeUnload`, CSS `#pensionAgentDemo` 범위, 기존 1 HTML + 1 JS + 1 CSS 반입을 유지한다.
- React/CDN/DOMContentLoaded 의존성이나 런타임 MD/PDF 파서를 추가하지 않는다.
- 패널 토글로 전체 화면을 갈아엎어 포커스·스크롤을 초기화하지 않는다. 고객 버튼으로 포커스 복귀, Esc/닫기 동작도 확인한다.
- Agent 수정 시 플랫폼 02 문서의 현재 구현 안내를 먼저 읽는다. 과거 LLM 절을 현재 동작으로 오해하지 않는다. 새 Python 파일은 평면 import와 Dockerfile 개별 COPY를 지킨다.
- 기존 llm_client.call·패키지·인증 경로는 이번 목적만으로 바꾸지 않는다. secret을 코드/로그에 저장하지 않는다.
- 생성된 반입본/Agent 묶음은 빌드로 갱신한다. 요청 없는 commit/push/사내 배포를 하지 않는다.

검증:

1. JSON의 16개 고객 필드·52개 브리핑 포인터가 현재 원본 값과 일치한다.
2. RAW 11개의 범위·문자열·SHA-256이 실제 corpus 파일과 일치한다. 출처 제목과 원문 파일 연결도 대조한다.
3. 현재 브리핑 JSON이 그대로이며 상품 3개·예상 반응 3개·액션 4개·팁 1개가 유지된다.
4. 오세훈 응답/패널, 근거 없는 기존 응답, 다른 고객, 취소·재요청·실패·고객 전환을 확인한다.
5. 기본 네 단계가 과도한 JSON/메타정보 없이 보이며 원문→반영 문장을 쉽게 찾을 수 있다.
6. 기존 부점 검색·엑셀과 축약된 메인 이력이 동작한다.
7. `node tools/briefing/build.js`, `node tools/briefing/check.js`, Agent 수정 후 `node tools/briefing/check.js --agent`를 실행한다.
8. 구조 PASS, 원문 대조, 로컬 UI, 사내 E2E를 구분한다. HTTP 검사 SKIP을 숨기지 않는다.

자료 준비 시 검증(2026-09-28): 고객 필드 16개, 화면 문자열 52개 전수 연결, 원문 조각 11개 문자열/해시, 내부 ID와 역방향 연결, 상대 링크, 기준일 D-10 대조 PASS. `node tools/briefing/build.js`, `node tools/briefing/check.js` PASS. 이 자료 작성에서는 Agent Python을 수정하지 않았으므로 `--agent`/HTTP 검사는 실행하지 않았다. 새 패널은 아직 구현 전이며, 원 PDF/사내 E2E 검증을 의미하지 않는다. 구현 후 위 검증을 다시 수행한다.
